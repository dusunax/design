# 보안 점검 규칙

## ID

- 점검 차수마다 `SEC-n`을 하나 붙인다. 점검 항목은 `SEC-n.k`다. 다음 차수에서 같은 항목을 다시 다뤄도 원래 번호로 부른다.

## 심각도

항목마다 두 가지를 적고, 아래 표에서 등급을 찾는다.

- **피해**: 일어나면 무엇이 망가지는가
- **필요 조건**: 피해가 일어나려면 무엇이 더 있어야 하는가. 필요한 게 적을수록 일어나기 쉽고, 등급이 높다.

| 피해 \ 필요 조건 | 없음 (바로 일어남) | 1개 | 2개 이상, 또는 검증된 방어가 막음 |
|---|---|---|---|
| 치명: 비밀값 유출, 코드 실행, 패키지 변조, 쓰기 권한 탈취 | 🔴 높음 | 🟡 중간 | 🟢 낮음 |
| 제한: 일부 데이터 노출, 피싱 | 🟡 중간 | 🟡 중간 | 🟢 낮음 |
| 경미: 성능 저하, 불편 | 🟢 낮음 | 🟢 낮음 | 🟢 낮음 |

- 필요 조건은 공격자가 갖춰야 하는 사건(프롬프트 인젝션, 토큰 유출, 상위 패키지 오염)과 운영자 실수(설정 실수)만 센다. 사용자의 정상적인 사용(클릭, 입력)은 세지 않는다.
- 기본 설정 그대로 쓸 때 생기면 필요 조건은 "없음"이다.
- 피해가 두 단계에 걸치면 높은 쪽으로 정한다.

| 등급 | 처리 |
|---|---|
| 🔴 높음 | 다음 MOA를 시작하기 전에 해결한다. 해결 Step이 끝나기 전에는 게이트를 통과하지 않는다 |
| 🟡 중간 | 게이트 SEC가 막는 MOA 안에 대책 Step을 넣거나, 넘길 차수를 정해 적는다 |
| 🟢 낮음 | 관련 Step에 넣거나 기록만 한다 |

### 근거

등급을 낮추는 근거(다른 방어가 막는다 등)는 테스트, 실측, 공식 문서 중 하나로 확인된 것만 인정한다. 확인되지 않은 근거는 없는 것으로 계산하고, 확인할 Step을 적는다.

### 교차 확인

🔴 판정이거나 등급 경계에서 망설인 항목만 두 번째 검토자(서브에이전트 가능)에게 피해와 필요 조건을 주고 등급을 따로 매기게 한다. 판정이 다르면 이 기준의 문구를 고친다.

## 문서

다음 차수는 직전 SEC 문서의 열린 항목과 아래 "차수별 범위"만 보고 시작한다. 그 전 차수 문서는 항목 상세가 필요할 때만 연다.

- `reviews/<날짜>-SEC-n.md`에 쓴다. 날짜는 점검한 날이다.
- 머리말은 DOC-1을 따르고, 점검 대상을 `reviews`에 적는다.
- 본문 첫 줄에 전제(공개 범위, 입력 출처 등)를 쓴다.
- 본문 순서: 요약 표 → 항목별 상세(위험, 피해, 필요 조건, 근거, 대책, 검증) → 문제없다고 본 것 → 열린 항목.
- 열린 항목 표(항목, 등급, 남은 일, 처리 시점)에는 끝나지 않은 일을 모두 적는다. 직전 차수의 열린 항목 중 끝나지 않은 것도 옮겨 적고, 🟢 항목의 유지 조건도 넣는다.
- 확인하지 못한 항목은 "미확인"으로 두고 확인할 Step을 적는다. 확인하면 결과를 채운다.

## 결과 반영

- 고칠 것은 진행 중이거나 다음에 시작할 MOA ID에 Step으로 넣는다(`MOA-5.0a`처럼).
- 요약 표의 "반영" 열에 넣은 Step을 적는다.

## 차수별 범위

| ID | 범위 |
|---|---|
| SEC-1 | 스펙(DOC-5)과 플랜(DOC-6) |
| SEC-2 | MOA-1\~MOA-4의 실제 코드. Text 파서와 링크 판정, Image, `dist` 결과물, `ci.yml`. MOA-5에서 처음 secret과 npm 배포가 들어오므로 그 전에 점검한다. 직전 열린 항목 중 처리 시점이 SEC-2인 것도 다룬다 |
| SEC-3 | 다음 패키지 설계(DOC-7, DOC-8). 직전 열린 항목 중 처리 시점이 SEC-3인 것의 대책을 확정한다. DOC-8에서 만드는 구현 ID의 게이트가 된다 |

차수를 추가하면 이 표에 범위를 넣는다.
