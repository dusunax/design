# 문서 작성 규칙

## ID 체계

| 접두사 | 대상 | 결과물 | 브랜치·PR |
|---|---|---|---|
| `MOA-n` | 구현 | 코드 | ID 하나에 브랜치 하나, PR 하나 |
| `SEC-n` | 보안 점검 | 점검 문서 | 없음 |
| `DOC-n` | 스펙, 플랜, 규칙 | 문서 | 없음 |

- 문서 하나에 ID 하나다. SEC와 DOC는 작업과 결과 문서가 같은 ID를 쓴다.
- 번호는 접두사마다 따로 매기고, 한 번 쓴 번호는 다시 쓰지 않는다.
- ID의 순서, 상태, 위치는 DOC-3에만 적는다. 진행 절차는 DOC-4에 있다.

## 머리말

모든 문서는 맨 위에 YAML 머리말을 둔다. 머리말만 읽어도 무엇을 다루는지와 언제 읽어야 하는지 알 수 있어야 한다.

```yaml
---
id: DOC-n
type: spec | plan | review | rules | index
title: 문서 제목
description: >
  무엇을 다루는지 한 문장.
  언제 읽는지 한 문장.
---
```

| 필드 | 규칙 |
|---|---|
| `id` | 이 문서의 ID. review는 `SEC-n`, 나머지는 `DOC-n` |
| `type` | 아래 "문서 종류" 중 하나 |
| `title` | 본문 `#` 제목과 같게 쓴다 |
| `description` | 두 문장. 첫 문장은 다루는 내용, 둘째 문장은 "\~할 때 읽는다" 형식의 읽는 시점 |

상태, 날짜, 관련 ID는 머리말에 쓰지 않는다. 상태는 DOC-3, 날짜는 git 기록에 있다.

review 문서만 점검 대상을 `reviews`에 적는다.

```yaml
reviews: [DOC-5, DOC-6]
```

다른 관계가 필요해지면 Jira 이슈 링크처럼 바깥·안쪽 방향(예: `blocks` / `is_blocked_by`)을 정해 이 문서에 추가하고, 관계를 만든 쪽 문서에만 바깥 방향을 적는다.

## 문서 종류

| `type` | 위치 | 파일 이름 |
|---|---|---|
| `spec` | `specs/` | `<날짜>-<주제>-design.md` |
| `plan` | `plans/` | `<날짜>-<주제>.md` |
| `review` | `reviews/` | `<날짜>-SEC-n.md` |
| `rules` | `docs/` 바로 아래 | `<대상>-RULES.md` |
| `index` | `docs/` 바로 아래 | `INDEX.md` (하나만 둔다) |

문서를 만들거나 옮기면 같은 커밋에서 DOC-3에 행을 넣거나 `위치`를 고친다.

### plan 본문

```markdown
# <주제> Implementation Plan

근거: DOC-n (스펙)

## Global Constraints
## MOA-n <내용>
- 브랜치 `MOA-n` · PR `<제목>` (머지 방식이 squash가 아니면 적는다)

### <소제목>
- [ ] **MOA-n.1: <할 일>**
```

### review 본문

DOC-2의 "문서" 절을 따른다.

## 본문 표기

- 한국어 `~다` 체로 쓴다.
- 코드 밖의 `~`는 `\~`로 쓴다. 범위 표기 두 개가 취소선으로 바뀌는 것을 막기 위해서다. 머리말 안에서는 이스케이프하지 않는다.
- 등급은 `🔴 높음`, `🟡 중간`, `🟢 낮음`처럼 이모지를 붙여 쓴다. 등급을 쓰는 규칙 문서에 등급별 기준을 둔다(보안 심각도는 DOC-2).
- Storybook MDX는 GFM 표를 렌더링하지 않는다. MDX에서는 표 대신 목록을 쓴다.
- 목록 항목은 `~다`로 끝내지 않고 명사형으로 끝낸다.
- 표는 처음 보는 사람 기준으로 쓴다. 열·행 제목은 뜻이 바로 읽히는 말로 쓰고(`0개`보다 `없음 (바로 일어남)`), 숫자나 기호만으로 의미를 전하지 않는다. 축이 두 개인 표는 위에 각 축의 뜻과 읽는 방향을 한 줄씩 적는다.
- 다른 문서는 ID로 부른다. 경로는 DOC-3에서 찾는다.
- 다른 문서에 있는 내용은 반복하지 않고 ID로 참조한다.
